# 产品愿景与阶段边界

## 为什么另起炉灶

现有 Readest 已积累大量阅读能力和跨端修复，但应用层同时承载账户、同步、在线服务、AI、TTS、翻译、词典、OPDS、RSS 与多种平台兼容层。继续在原项目上裁剪，会让新产品在理解成本、构建体积、状态耦合和演进风险上持续背负历史重量。

AI Reader 改为从空仓库逐步构建。它借鉴 Readest 已验证的代码与架构，尤其复用 `foliate-js` 分支和 PDF.js；但每个 Module 都在明确 Interface、数据所有权和验收 Seam 后再引入。目标不是复制目录树，而是把阅读器如何成立的过程变得可理解、可测试、可替换。

## 产品方向

长期产品仍面向文史哲兴趣学习者，最终让阅读、多材料并排比较、提问和轻量知识积累发生在同一个阅读工作区中。第一阶段先证明阅读工作区本身可靠；只有这一基础稳定，后续 AI 才能获得明确的材料身份、主材料、章节位置、普通批注和 Markdown 笔记载体。

## 第一版承诺

- Windows、macOS、iPadOS 和 Android 平板；Windows 是主要开发与完整验收平台。
- 本地 EPUB、PDF、Markdown 导入和应用内托管。
- 传统封面书库、标题/作者筛选、元数据覆盖和内部回收站。
- 类 VS Code 的单窗口工作台、多个标签、最多两个编辑器组、活动视图与显式主要阅读材料。
- EPUB 基本排版，PDF 翻页/缩放/文本选择，Markdown 阅读与源码编辑。
- 当前材料全文搜索、目录、书内链接、导航历史。
- 普通高亮、文字笔记、扫描 PDF 区域高亮与页内批注。
- 工作区、位置、排版、批注和编辑恢复快照的可靠持久化。
- 完整书库快照备份和整库原子恢复。
- 全中文界面。

## 第一版明确不做

- 任何 AI、Agent、知识包、自动摘要或 AI 目录。
- 账户、云同步、端到端加密、共享与协作。
- OCR。
- TTS、翻译、词典、OPDS、RSS、在线书库和发送到设备。
- 手机、Linux 和完整 Web 产品。
- 多原生窗口、递归分栏、四宫格或无限编辑器组。
- 全书库正文索引、正则/模糊/语义搜索。
- 互动 EPUB 脚本和书籍远程资源。
- 从既有 Readest 安装或数据就地迁移。

## 后续 AI 方向的继承约束

后续 AI 功能必须建立在当前阅读领域之上，而不能修改其基本语义：

- 主要阅读材料由用户显式指定，焦点变化不得偷偷改变 Agent 归属。
- Agent Runtime 通过可替换 Interface 隔离，不能把具体 SDK 类型传入 Workbench 或 Reader。
- 书籍 Agent 从模板复制后成为独立配置，不具备隐藏长期记忆。
- 伴读对话对用户完整可见，不把旧对话隐式注入新对话。
- 趣味技能必须主动触发，只能使用白名单工具，不执行任意代码。
- 书籍知识采用书籍索引、章节知识笔记、原文章节片段的渐进披露结构，初始实现不依赖向量 RAG。
- AI 笔记以 Markdown 作为规范内容，能直接复用第一版的 Markdown Reading Material、编辑与锚点能力。
- 同步后端仅作为端到端加密副本的可替换传输渠道，不拥有领域规则，不同步原始书籍、API Key、伴读对话或运行时状态。
- 跨端加密验证如果不能通过，产品必须保持本地可用并延期同步，不能退化为服务器可读明文。

## 与旧设计的关系

以下早期结论继续有效：四个平台目标、独立产品、集中拥有工作区状态、未来可替换 Agent Runtime、模板化无长期记忆 Agent、三层书籍知识和端到端加密同步原则。

以下早期结论被当前方案覆盖：

- “从 Readest 当前 main 裁剪”被“空仓库逐步实现并选择性借鉴”覆盖。
- “沿用 Readest 抽样 MD5 与 metaHash”被“稳定 BookId + 完整内容指纹”覆盖。
- AI、账户与同步不再属于第一版，而是后续阶段。
